# Mrs. Smith — Plan (v1)

Карманный репетитор английского. Один персонаж, один режим, бесплатно.
Проще "дипломной работы": чистый, понятный продукт без побочных веток.

**Название:** Mrs. Smith — без отдельного бренда поверх персонажа.
Telegram-хендл: `@MrsSmithBot` (если занят — `@MrsSmithTutorBot`;
проверить занятость хендла нужно вручную, Telegram API недоступен из
этой сессии).

Решения ниже зафиксированы в разговоре 2026-10-08 — этот файл их записывает,
а не придумывает заново. Код пока не пишем.

## Что это

- Telegram-бот, один персонаж — **Mrs. Smith** (английская учительница,
  20+ лет опыта, Portland). Бэкстори/голос персонажа переносим из
  speechflow (`personas.py`, ключ `mrs_smith`) почти без изменений — это
  уже рабочий, проверенный на пользователях характер.
- Один режим — аналог Tutor Mode: разговор + коррекция ошибок в одном
  ответе. Никаких PenFriend/Flow/других персонажей в v1.
- Бесплатно, без paywall, без Stars. Монетизация — вопрос другого дня.

## Почему новый код, а не перенос файлов

Код пишем с нуля, но переносим уже проверенные в проде решения из
speechflow, а не изобретаем заново:

- **Groq API** (`openai/gpt-oss-120b`) с мульти-ключевой ротацией.
- **Guard против think-leak** — у gpt-oss-120b бывает, что reasoning
  утекает в `message.content` (`<think>...</think>` или без закрывающего
  тега), съедая весь `max_tokens` и оставляя пустой ответ. В speechflow
  на это ушло несколько раундов багфиксов (`_extract_text()` helper) —
  здесь закладываем его с первого дня, а не после жалоб пользователей.
- **Supabase с первого дня**, не как заплатка после — в speechflow
  кэш переводов и rate-limit сначала жили в памяти процесса и терялись
  на каждом рестарте; здесь сразу пишем в БД.
- **DB-backed rate-limit** (burst-защита от спама) — тоже с первого дня,
  по той же причине.

## Коррекция ошибок — единый промпт

В speechflow коррекция — два отдельных LLM-вызова (ответ персонажа +
отдельная карточка ❌/✅/💡) плюс переключатели Recasting/Mistakes
Practice. Для Mrs. Smith берём более простую архитектуру: один вызов,
один промпт, разговор и коррекция в одном ответе — набросок уже есть в
`roadmap.md` speechflow (раздел "Mrs. Smith / Tutor Mode — полный
редизайн"). Адаптация под персонажа:

- Персона Mrs. Smith из speechflow сейчас явно говорит "a separate
  system handles grammar correction, you do NOT correct errors" — это
  старая архитектура. В новом промпте это утверждение убирается:
  коррекция становится частью её собственного голоса, а не отдельной
  системы.
- Правила коррекции (из присланного Gemini-промпта, уже в roadmap.md):
  - 1-2 самые значимые ошибки за сообщение, не разбор каждой мелочи
  - не повторять одну категорию ошибок подряд, если это не системная
    (повторяющаяся) ошибка
  - 3+ повтора одной ошибки за сессию → перестать просто исправлять,
    попросить юзера самому использовать правильную форму
  - коррекция никогда не последняя часть ответа — всегда продолжение
    разговора после неё
- Формат ответа: `[Correction]` (коротко, с одной причиной) +
  `[Conversation]` (полноценная реплика персонажа) в одном сообщении.

## Пользовательский флоу v1

1. `/start` → короткий онбординг: имя + уровень английского (2-3
   реплики, не форма). Без английского варианта имени, без выбора
   цели — это не MVP-критично, можно добавить позже.
2. Чат с Mrs. Smith — разговор + коррекция в одном ответе (текст).
3. Голосовые ответы (TTS) — Mrs. Smith отвечает голосом, как в
   speechflow (голос `diana`). Нужно решить: всегда голосом, только в
   ответ на голосовое сообщение юзера (mirror), или настройка — пока
   предлагаю **mirror** (голосовым — голосом, текстом — текстом) как
   более естественный дефолт для "учителя", без отдельной настройки в
   v1.
4. Session Summary по запросу, при выходе — **и автоматически при
   достижении дневного лимита** (см. лимиты ниже): вместо "приходи
   завтра" юзер получает осмысленное завершение дня — голосовое
   сообщение с разбором ошибок/прогресса сессии (как в текущем
   speechflow, уже voice-based, не PDF).

## Данные — Postgres на Neon, прямой SQL

Решено (2026-10-08, после сравнения вариантов):

- **Хостинг — Neon**, не Supabase и не Render Postgres.
  - Render Postgres free отпадает: истекает через 30 дней + 14 дней
    грейс-периода, потом Render удаляет БД со всеми данными — не
    годится для долгоживущего бота.
  - Supabase (как в speechflow) рабочий вариант, но free-проект ставится
    на паузу после ~7 дней без активности и снимается с паузы вручную
    через дашборд — риск, что бот "молчит", если про него забыли.
  - Neon: compute засыпает после 5 минут простоя, но просыпается сама
    за ~500мс на следующий запрос — без ручных действий. Без кредитки,
    без срока истечения.
- **Доступ — напрямую через `asyncpg`**, без REST-слоя (как
  `supabase-py` в speechflow) и без ORM (SQLAlchemy — лишний вес для
  плоской архитектуры). Пишем SQL сами, `db.py` — плоский модуль с
  async-методами, как `supabase_db.py` в speechflow, только без
  посредника.
- **Миграции — версионированные `.sql`-файлы** в `migrations/`
  (`001_init.sql`, `002_...`), применяются одной и той же командой и
  локально, и на Neon — никаких ручных ALTER TABLE через веб-редактор.
- **Локальная разработка** — Postgres в Docker на машине разработчика
  (не в cloud-сессии — она не хранит состояние между запусками).
  Единственная точка конфигурации — `DATABASE_URL` в `.env`: локально
  указывает на Docker-Postgres, на Render (прод) — на Neon. Код `db.py`
  не знает и не должен знать, с каким Postgres он говорит.

### Схема (минимальная, без платёжного/тарифного)

- `users`: telegram_id, name, level, created_at, last_active,
  burst_message_count/burst_window_start/burst_cooldown_until
  (rate-limit с первого дня, см. выше)
- `messages`: user_id, role, text, telegram_message_id, created_at
  (нужно для Text/Translate-кнопок и контекста разговора)
- `error_logs`: user_id, category, mistake_text, corrected_text,
  created_at (для Session Summary и на будущее — своя версия
  Vocabulary/Mistakes экрана, если понадобится)

## Админ-панель — в скоупе v1

Это диплом — БД должна быть видна и использована "на всю катушку", не
спрятана за продуктовым UI. Админ-панель = витрина данных:

- Общая статистика: кол-во юзеров, сообщений за день/неделю, активные
  юзеры, распределение по уровням английского
- Разбор ошибок по категориям (агрегация по `error_logs`) — частотный
  анализ, что чаще всего путают
- Карточка юзера: история сообщений, прогресс, уровень, когда последний
  раз заходил
- Доступ — по `ADMIN_IDS` из `.env`, как в speechflow

## Лимиты и контекст — зафиксировано

- **10 бесплатных пар сообщений в сутки** (пара = сообщение юзера +
  ответ Mrs. Smith). При достижении — автоматический Session Summary
  (см. флоу выше), не "купи Pro" и не глухая стена.
- **Контекстное окно — 5** последних сообщений в промпте.
- **Voice — `diana`**, без изменений.

## Деплой: polling + free Render Web Service

Проверено на практике (speechflow уже так работает стабильно):
**long polling** (бот сам стучится в Telegram), не webhook. Free Web
Service на Render засыпает после 15 минут без входящего HTTP — чтобы
он не засыпал, поднимаем лёгкий HTTP-сервер (`aiohttp`, который и так
тянется aiogram'ом — без отдельного FastAPI/uvicorn) с `/health`,
который внешний keep-alive пингует (UptimeRobot/cron-job.org или
аналог — настраивается отдельно от кода, не здесь).

## Структура проекта — зафиксирована

```
mrs-smith/
├── .env.example
├── requirements.txt
├── README.md
├── migrations/
│   └── 001_init.sql
└── src/
    ├── main.py        # Bot/Dispatcher, aiohttp /health, polling, запуск
    ├── config.py      # env-переменные, лимиты (10/день, контекст=5)
    ├── prompt.py       # системный промпт Mrs. Smith
    ├── db.py           # asyncpg pool, users/messages/error_logs, rate-limit
    ├── groq_client.py  # Groq: единый ответ (JSON: category/mistake/
    │                   # corrected/reply_text), Session Summary, TTS,
    │                   # think-leak guard
    ├── keyboards.py    # Text/Translate/Original, админ-кнопки
    ├── handlers.py     # /start, онбординг, сообщения, callback'и
    └── admin.py        # админ-панель (статистика, разбор по категориям)
```

Техническая деталь, уточняющая "единый промпт": чтобы админ-панель
могла агрегировать ошибки по категориям (`error_logs`), единственный
LLM-вызов на сообщение возвращает **structured JSON**, а не просто
текст с заголовками `[Correction]/[Conversation]` — внутри JSON есть
и поле с готовым текстом ответа (который реально увидит/услышит
юзер, написанный по всем её правилам речи), и отдельные поля
category/mistake/corrected для записи в БД. Это всё ещё один вызов —
меняется только формат вывода, не архитектура.
